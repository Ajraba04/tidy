## Findings

### PS01 — Scan ignores the selected scope and walks the home tree

- **Dimensions/workflow:** D08/D10/D14/D18, Settings → Scan. **Severity High; confidence high.** Requirement: default Quick is known-root bounded work; selectedProjects is limited to selected approved roots; full-home is a one-run request only (registry `scan.defaultScope`, design scan customization).
- **Expected/observed:** `scan.defaultScope` is persisted/resolved and editable, yet the app builds a legacy `CleanEnvironment` with no scope field (`Tidy/Scan/ScanViewModel.swift:43`), and `ScanEngine.swift:501` always starts `HomeSurvey.walkBounded` at `environment.homeDirectory`, then walks Library again at 539. No scope value is consumed anywhere in scan orchestration. Thus even selectedProjects with no selected roots traverses unrelated Documents; the normal Quick path also starts at home.
- **Minimal reproduction:** in an owned scratch home create Documents/witness.bin, save selectedProjects with no project roots through SettingsStore, bootstrap real bridge, run ScanEngine and inspect `topLevelHomeRanking`. Optional audit regression file exercises that production route and asserts the opposite, desired behavior. No runtime result claimed here.
- **Root cause/reachability:** policy is resolved for budget but root selection lives in legacy environment; every user who explicitly scans after policy installation reaches it. Reads only; this is not evidence of deletion or network access.
- **Correction/owner/dependencies:** scanning/policy owner, after approved scope-identity representation: derive an immutable exact root set from acknowledged policy and explicit request, pass it to production traversal, enforce it below UI, refuse selectedProjects without approved selections. Do not infer full-home consent from Run Scan.
- **Acceptance/regression:** scratch unrelated witness is not visited under Quick or selectedProjects; approved roots are visited; explicit one-run full-home works and expires; second window/policy-change race cannot expand roots. Closure requires production-bound metadata-visit evidence, not only empty final rows. Blocks current scan scope trust and full acceptance.

### PS02 — Critical pressure, thermal and power policy never reaches live scan scheduling

- **Dimensions/workflow:** D08/D10/D15/D18, scan under constrained conditions. **Severity High; confidence high.** Requirement: hard critical pause, configured LPM/serious-thermal restrictions, recovery delay and bounded sleep/wake behavior.
- **Expected/observed:** all production bridge preparations use `.unknown` (`ExecutionPolicyBridge.swift:738`, 744, 951). The only `SchedulerPolicyController.updateObservation` definition is internal (`WorkScheduler.swift:762`) and has no production caller. Unknown resolves lowPower/thermal/critical to false at 828 and restricts walks to one worker/user-requested mode at 841, but permits explicit scans during real critical conditions. SystemMonitor receives pressure only into its own field (`SystemMonitor.swift:439`). `scan.resumeAfterCriticalSeconds` has no scheduler consumer.
- **Minimal reproduction:** use production bridge with scratch policy, send controlled live-state observations at the monitor boundary while a bounded scan is waiting for its next batch. No bridge observation route exists; scheduler epoch/admission remain unchanged. Physical stress must not be induced on current host.
- **Root cause/reachability:** missing monitor/OS-observation-to-scheduler adapter; reachable for every explicit scan. Conservative unknown one-worker behavior is acknowledged and prevents claiming unconstrained four-worker fanout, but does not satisfy critical pause.
- **Correction/owner/dependencies:** platform scheduling owner; separate app-owned live resource observation from visible-only signal UI, retain observation while explicit scan is active, preserve zero hidden-idle work, drive monotonic epochs and cooldown with injectable clock, account for sleep/wake and missing observations.
- **Acceptance/regression:** production-wired injected critical transition stops new batches, releases bounded workers, survives window close, and resumes only after configured clear period; stale samples cannot reopen admission. Measure physical-host cancellation and constrained-host gates separately. Blocks low-impact guarantee and full acceptance.

### PS03 — Fresh-install Scan requires an unrelated settings write

- **Dimensions/workflow:** D01/D09/D10/D16, first launch → Run Scan. **Severity Medium; confidence high.** Requirement: usable explicit scan with conservative defaults and truthful recovery.
- **Expected/observed:** scheduler initial install only runs for positive revisions (`ExecutionPolicyBridge.swift:213`); pristine defaults have revision zero; `AppExecutionServices.swift:89` throws policyNotInstalled; `ScanViewModel.swift:50` tells user to open Settings and save once. The settings surface autosaves edits and has no corresponding universal Save workflow, so this is an artificial gate rather than missing consent. Scan tests explicitly seed positive revision (`ScanOrchestrationWiringTests.swift:34`).
- **Minimal reproduction:** new owned settings path, no prior save, bootstrap and request explicit scan. Audit probe tests real store/bridge snapshot. Onboarding completion may create a positive revision if completed; the defect specifically concerns the no-prior-save path required by the audit, not every post-onboarding launch.
- **Root cause:** coupling scheduler authority to persistence revision >0 instead of validated default configuration plus explicit user request.
- **Correction/owner:** settings/scheduler owner; admit validated pristine defaults without background work, or atomically persist defaults during explicit consent. Preserve malformed/future-schema failure boundaries.
- **Acceptance/regression:** pristine explicit scan succeeds; merely opening UI still launches no traversal; corrupt/future settings remain blocked with actionable recovery. Blocks fresh-install usability; bounded workaround is changing an editable preference.

### PS04 — Partial progress enables duplicate scans and discards continuation

- **Dimensions/workflow:** D05/D10/D16/D18, long scan → partial progress → Rescan/close/reopen. **Severity Medium; confidence high.**
- **Expected/observed:** progress changes the view phase to `.partial` (`ScanViewModel.swift:97`), and `.partial` enables Rescan (`ScanView.swift:94`). `runScan` detaches only the subscriber and begins a new session; `beginScan` has no single-active guard (`AppExecutionServices.swift:89`), replacing the sole active handle at 99. Previous work remains owned by registry and continues, but global Cancel/latestResult now address only the replacement. Existing old window can finish with “without a retained result.” Separately, all results set continuationAvailable=false and cursor-bearing home results invalidate the cursor (`ScanEngine.swift:514`); no Continue button exists. Large trees repeatedly restart instead of completing the approved time-sliced workflow.
- **Minimal reproduction:** two windows share a deliberately slow fixture scan; after first progress click Rescan in one window, close windows and use global Cancel. Verify original session remains active and cannot be addressed by global owner. Force a slice expiration using controlled clock; Continue is absent. This source path does not depend on mutators.
- **Correction/owner:** app/scanning owner; separate running partial presentation from terminal partial, prevent/attach duplicate starts, retain bounded handles indexed by session if concurrency intended, add generation-bound resumable cursor ownership and explicit Continue.
- **Acceptance/regression:** double-click/rescan/progress/two-window races maintain one intended scan or a complete bounded global task list; global Cancel addresses all intended explicit work; no lost final result; sliced scan eventually equals fresh walk without rescanning completed segments. Blocks current progress/cancel correctness and T08 full acceptance.

### PS05 — Shared monitor visibility and policy updates are not scene-safe

- **Dimensions/workflow:** D08/D11/D18, Headroom plus menu popover/Settings. **Severity Medium; confidence high.**
- **Expected/observed:** `SystemMonitor.swift:299` stores one `isWindowVisible` Boolean; Headroom (`HeadroomViewModel.swift:58`,67) and popover (`StatsRefresher.swift:56`,68) independently set it. Closing either surface sets false and stops sampling although the other is visible (`SystemMonitor.swift:398`). Settings changes are applied only on appearance (`HeadroomView.swift:39`, `StatsRefresher.swift:74`), so changing interval/history/feature settings in another window does not promptly affect an already-open Headroom. `ui.cards` is frozen at construction and an intentionally empty list becomes all cards (`HeadroomViewModel.swift:28`).
- **Minimal reproduction:** Headroom visible → open popover → close popover → leave Headroom visible past its interval; measurements stop. Disable headroom or raw history in Settings without reopening Headroom; old configuration remains active.
- **Root cause:** shared actor is correct, but visibility is not keyed to consumers and no shared configuration observer publishes acknowledged changes.
- **Correction/owner:** app state/monitor owner; idempotent per-scene visibility leases and one acknowledged-policy subscriber; preserve empty card subset and update presentation without invalidating confirmations.
- **Acceptance/regression:** two visible surfaces, either-order closure, duplicate disappear, two-window policy revocation, teardown subscriber counts and hidden-idle zero-work all pass through actual view models. Blocks live-signal reliability; no invented physical-runtime evidence.

## Optional audit probes and reproducibility limits

`PolicyAuditRegressionTests.swift` is an audit-only test source to copy into an isolated worktree test target. It asserts approved behavior for pristine scheduler availability and selectedProjects scope through production SettingsStore/bridge/ScanEngine. It intentionally does not alter the audited baseline. Coordinator owns compilation/result/log evidence and whether source-confirmed findings become runtime-confirmed.

`PolicyAuditPerformanceTests.swift` similarly measures production no-index filesystem orchestration with 50k/100k zero-length files, two unchanged passes, 20 immediate cancellation cycles per fixture and a protected witness. Process stage is replaced with a no-op recording boundary, so results are **filesystem-path measurements, not full-app performance acceptance**. It reports processed entries (not OS metadata syscall counts), coverage reasons, first useful result, elapsed monotonic time, worker/queue counts and `/dev/fd` counts. Fixture creation is excluded from reported scan time. External max RSS includes harness and setup and is not physical footprint; no isolated steady-state memory or build-interference claim is possible from this test. Partial coverage must remain a usefulness failure even if the test exits 0. Warmup/repetitions/variance/reference-hardware evidence must be supplied separately to satisfy T23.

No current-primary-vendor API claims were needed to confirm the source wiring defects.
